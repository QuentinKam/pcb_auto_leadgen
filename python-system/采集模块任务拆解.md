## 一、采集约束（原 spec §3.1）

- 生产采集任务**仅运行于云侧 worker**；本地仅用于开发调试小样本
- 遵守 robots.txt；请求间隔随机 1–3s；每域名并发 = 1
- 失败熔断：连续 5 次 4xx/5xx → 冷却 10 分钟
- 目标行业：机器人、工控、医疗电子、车载硬件等 PCB 高需求行业
- 输出：原始企业数据集（企业 + 关键决策人 + 邮箱）

## 二、前置依赖（原 P0）

- **P0.2 ORM 模型 + Pydantic Schemas** —— 采集产物要有落库契约
- **P0.3 数据清洗管线（TDD）** —— 邮箱校验、域名/企业名双维度去重、脏数据过滤

> 对应本仓库现状：`packages/db` 已有 Drizzle schema，清洗管线尚无。

## 三、P1 任务拆解

### P1.1 搜索 API 客户端（可切换，免费额度起步）

- 依赖：P0.2
- 任务：
  - 抽象基类 `SearchClient`：`async search(query, country=None) -> list[SearchHit]`
  - **首发实现 `BraveSearchClient`**：免费额度起步，OpenAPI 契约一致
  - 通过 `Settings().search_provider` + 工厂函数 `get_search_client()` 切换供应商
  - 预留 `TavilySearchClient`、`SerpApiClient` 接口契约（仅签名 + TODO，不实现）
  - 所有 HTTP 走统一客户端，用 respx 做 mock 单测
- 验收：
  - 单测覆盖响应解析、限流头（`X-RateLimit-Remaining`）回读、429 指数退避
  - 切换 `SEARCH_PROVIDER=tavily` 时工厂返回对应实现（mock 路径命中）
- 业务价值：零成本先跑通；后续付费额度或换供应商可无缝切换

### P1.2 官网静态抓取

- 依赖：P1.1
- 任务：
  - `httpx_fetch`：超时 / 重试 / UA 轮换
  - `curl_cffi_fetch`：TLS 指纹绕过（按需启用）
  - 抽 `SiteFetcher` 抽象，运行时按 `Settings().site_fetcher` 切换 httpx / curl_cffi / Playwright
- 验收：抓 3 个公开站点 HTML 入 `ScrapeSnapshot`；respx mock 测试通过
- 业务价值：**企业官网是 RAG 研判的核心信息源**

### P1.3 Playwright 动态渲染（按需降级）

- 依赖：P1.2
- 任务：
  - 安装 Playwright + chromium
  - 实现 `playwright_fetcher.py`
  - **仅在 httpx 拿不到正文 / 检测到强 JS 渲染时降级使用**
- 验收：动态站点（React SPA 样例）能拿到完整 HTML
- 业务价值：突破反爬盲区，提升数据完整度

### P1.4 限流熔断

- 依赖：P1.2
- 任务：
  - 令牌桶限流（**按域名 / 全局双维度**）
  - 每域名并发 = 1 信号量
  - 随机请求间隔（1–3s）
  - 失败计数熔断（连续 5 次 4xx/5xx → 冷却 10 分钟）
- 验收：单测验证限流计数、熔断状态机
- 业务价值：防封禁，对应 AGENTS.md §8 法律合规红线

### P1.5 联系人 / 邮箱萃取

- 依赖：P1.2
- 任务：
  - `trafilatura` 抽正文 + 正则 + LLM 抽邮箱 / 职位
  - 命中 `Contact` 表，触发 P0.3 邮箱校验（MX 可达性）
- 验收：给定官网 HTML 能萃取至少 1 个有效邮箱（样例站点）
- 业务价值：邮件触达的基础字段

## 四、原技术选型要点（spec §4.2.2，Python 栈）

| 项 | 选型 | 理由 / 降级策略 |
|---|---|---|
| 搜索引擎获客 | 搜索 API 优先：Tavily / Brave / SerpAPI | API 稳定合规、不封 IP；预算为零时降级 Playwright + 住宅代理 |
| 静态页抓取 | httpx + selectolax | 异步快、解析性能高 |
| TLS 指纹绕过 | curl_cffi（impersonate Chrome） | 过 Cloudflare 等基础 WAF |
| 动态页渲染 | Playwright (Python) 1.50+ | headless 浏览器事实标准；规模扩大后升级 Crawlee Python（会话池/代理池内置，省 90% 浏览器资源） |
| 正文抽取（喂 RAG） | trafilatura 本地抽取 | 本地零成本；难解析站点降级 Jina Reader / Firecrawl API |
| 代理 | 住宅代理按流量计（Bright Data / Oxylabs / Smartproxy） | 内部低频用量小；仅搜索/强反爬站点使用 |
| 风控 | 自研令牌桶 + 随机间隔 + UA 轮换 + 每域名并发=1 | 尊重 robots；封禁自动熔断；**生产仅跑云侧 worker** |

### 若在本仓库（Bun 栈）落地，等价选型建议

| 原 Python 选型 | Bun / Node 等价物 | 备注 |
|---|---|---|
| httpx | 内置 `fetch` / undici | 直接可用 |
| selectolax | `cheerio` / `node-html-parser` | 解析能力相当 |
| curl_cffi | **无直接等价** | Bun fetch 无 TLS 指纹伪装能力，强反爬站点需外接代理服务或 headless |
| Playwright (Python) | `playwright` (JS) | 同名，API 接近 |
| trafilatura | `@mozilla/readability` + `jsdom` | 正文抽取效果接近 |
| rapidfuzz | `fastest-levenshtein` / `fuse.js` | 企业名模糊匹配 |
| dnspython MX 校验 | `node:dns` 的 `resolveMx` | 内置 |
| 令牌桶限流 | `bottleneck` 或自研 | 需支持按域名分桶 |

> 与 `AGENTS.md` 的一致性：原方案的 Crawlee + Playwright + 代理池，
> 与本仓库 `AGENTS.md` §2 声明的采集栈一致，可直接沿用其合规约束（间隔 ≥2s 等）。

## 五、原分阶段落地顺序（spec §4.5，供排期参考）

### 阶段 1（MVP 闭环）

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 | PG 表结构（含绩效溯源字段）+ 模型 + 清洗去重管线（TDD） | 脏数据 CSV 进、干净线索出，去重/邮箱校验可测 |
| P1 | 采集模块：搜索 API + 官网抓取 + 限流 | 按国家 × 行业产出原始企业数据集 |
| P2 | PCB 行业 RAG 知识库 + 评分 Agent | 输出 A/B/C 分级 + 研判理由，人工抽检准确率 |
| P3 | 邮件生成 + 发送（域名预热 + GDPR 退订）+ 回信解析 + 退信黑名单 | 个性化邮件合规可发，回信自动分类打标 |
| P4 | 调度 + 任务状态机串联端到端 + **云上生产部署（下线本地 PC）** | 全链路云侧无人值守跑通，失败可重试 |
| P5 | 自建简易 CRM + 在线客服迁移 + 看板 + 成本追踪 | 业务员跟进至报价/成交标记，看板出 OKR 指标 |

### 阶段 2（完整业务闭环）

| 阶段 | 内容 | 验收 |

多租户、合规数据源替换、多行业知识库、可视化配置、计费。
