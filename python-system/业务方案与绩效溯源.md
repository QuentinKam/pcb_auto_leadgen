# 业务方案与绩效溯源（归档）

> 来源：原 `PCB_ALL/pcb` 仓库的 `intent.md` / `intent_v2.md` / `spec.md` §5–§6 / `spec_v2.md`。
> 这些是**客户业务层**内容，本仓库（`pcb_auto_leadgen`）作为产品仓库完全没有，故保留。

---

## 一、业务现状与痛点（项目起点）

业务主体：PCB/PCBA 一站式制造外贸，主攻欧美市场。

- 本地电脑跑「自动找客户 + 自动发邮件」脚本已运行 **1 个月，0 回复**
- **无 CRM、无企业邮件发送体系**；仅有自有独立官网
- 本地 PC 充当服务器，官网在线客服**响应缓慢**

## 二、根因诊断与修复优先级

推测 0 回复的根因有四个：

1. 本地裸跑导致 **IP / 域名信誉受损**（最可能的主因）
2. 客户筛选粗糙——抓到邮箱就群发，没有资格预审
3. 发送策略不当——无时区错峰、无频率管控、无域名预热
4. 内容同质化——模板群发，无个性化

**结论口径**：优先修复底座（云侧发送 + 域名信誉 + 筛选精度 + 内容个性化），**再谈规模撒网**。
不要在没有修复底座的情况下加大发送量，否则会进一步损坏域名信誉。

## 三、三阶段路线

### 阶段 1｜MVP 闭环（最高优先级）

1. 淘汰本地 PC 生产运行模式，迁移上云，修复邮件发送信誉，解决 0 回复
2. 补齐基础底座：自建简易 CRM 线索库、合规邮件发送能力；在线客服迁云
3. 跑通：公开客户挖掘 → AI 行业研判打分 → 可控批量个性化邮件触达 → 回信 AI 解析 → 线索入库
4. 产出可被业务员跟进的合格海外 PCB 潜在客户，拿到真实回复与询盘

### 阶段 2｜完整业务闭环

1. AI 被动内容流水线：基于 PCB 行业知识库产出英文文章、短视频脚本，供官网 SEO / 海外社媒引流
2. 业务员辅助工具：线索管理、客户调研、邮件改写、跟进提醒
3. 主动挖掘线索 + 官网被动留资线索**统一归集**，全链路业务指标看板

### 阶段 3｜远期可选：软件产品化

> 前置条件：内部业务完整跑通并验证效果，否则不启动。

系统标准化改造：多租户隔离、可视化配置界面、多行业知识库适配、
合规改造（替换高风险爬虫数据源、GDPR 适配）、计费能力。

## 四、硬性边界约束（客户侧，重要）

### 产品边界

1. **阶段 1、阶段 2 定位内部自用系统，不对外售卖软件**；产品化为阶段 3 可选目标
2. **单租户**；不面向外部用户，无注册、无权限体系、无计费
3. 业务唯一服务对象：本公司 PCB 外贸业务
4. 收益来源是 **PCB 加工订单，不靠软件本身盈利**

### 合规边界

1. 邮件发送不追求「无脑快速撒网」，欧美 GDPR 合规优先，保护域名与 IP 信誉
2. 爬虫仅内部业务低频使用，不做公网公开服务；不售卖、不流转数据、不对外提供抓取接口
3. 批量发送仅服务企业合法商务推广，严控频率，正文带退订通道

### 基础设施边界

1. **废弃本地 PC 生产运行模式**，全部生产负载（爬虫、发信、在线客服）迁云
2. 本地机器仅保留开发调试用途

### 技术边界

1. 不自研大模型，纯应用层开发，只调用主流大模型 API
2. 阶段 1–2 行业知识库固定垂直 PCB 领域，不通用全行业
3. **AI 只放大业务效率，不能替代业务员商务谈判、报价**

## 五、绩效与线索溯源设计（本仓库缺失，重点保留）

系统需要在线索表记录以下溯源字段：

| 字段 | 含义 |
|---|---|
| `lead_source` | 线索来源：`ai_outbound`（AI 主动挖掘）/ `website_inbound`（官网被动引流）/ 其他 |
| `is_ai_generated_lead` | 布尔标记：是否为本系统产出线索 |
| `quoted_at` | 报价时间；标记该线索是否产生正式报价 |
| `deal_closed_at` | 成交时间；标记线索是否最终成交订单 |

**用途**：支撑混合绩效方案——

> 基础薪资 + AI 合格线索产生报价绩效点 + 后续成交追加提成

**待业务侧定义**：什么是「**合格 AI 线索**」（需要业务侧共同确认，不能由技术单方面定义）。

**为什么需要区分两个节点**：PCB 欧美客户成交周期长达数月，
因此必须把「AI 线索产生正式报价」与「线索最终成交」拆成两个独立业务节点分别记账，
否则绩效无法落地。

## 六、本仓库尚未覆盖的模块

`pcb_auto_leadgen` 目前没有实现、但客户方案里有明确设计的两块：

### 1. 回信 AI 语义解析

- 自动读取收件邮件
- 语义分类：**有意向 / 无意向 / 询价 / 索要资料 / 拒收 / 退订 / 自动回复 / 垃圾邮件**
- 自动打标签、更新线索状态
- 高价值询盘自动置顶预警

> 本仓库现状：`apps/mailer` 只有 Resend webhook 事件回收（送达/退信/投诉），
> **没有回信意图解析与打标**。

### 2. 官网在线客服改造

- 将本地服务器运行的在线客服迁移至云端（SaaS 或云上自托管，如 Chatwoot），解决响应慢
- 访客留资经 webhook **自动写入线索库**（`lead_source = website_inbound`）

## 七、需要业务侧确认的输入

1. 云、邮件服务等第三方基础设施**预算范围**
2. **业务员人数**，每日可承接新线索上限
3. 官网现有访问与询盘**基线**
4. 业务对优质线索（A/B 级）的**数量预期**

## 八、两种定位的差异对照

| 维度 | 内部自用版（原 `pcb`，阶段 1–2） | 对外产品版（本仓库方向） |
|---|---|---|
| 目标 | 优先追求业务效果 | 产品化、可规模售卖 |
| 实现方式 | 允许一定「野路子」，工程师可用即可 | 必须多租户、UI 面向非技术用户 |
| 合规 | 内部小流量，风险可控 | 必须规避爬虫与邮件合规风险，改用采购商业线索库 |
| 工作量 | 原型 | 产品化工作量是原型的 2–3 倍 |
| 市场 | 无外部竞争 | 面临激烈市场竞争 |

> 结论：本仓库已选择走产品版方向，因此原 `pcb` 的单租户内部版方案不再单独维护；
> 但其**绩效溯源设计**与**客户业务约束**对产品版仍有参考价值（例如多租户下如何按租户配置绩效口径）。
