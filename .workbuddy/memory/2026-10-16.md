## 代码评审：agent 成熟度评估（程枢视角，实跑验证）

按「生产级八项」标准评审全仓库，结论：**工程素养高于一般 demo，但仍在 demo 与生产之间（偏生产侧半成品）**。八项缺 3-4 项。

### 定性：这不是严格意义的 Agent
Agent = LLM + Tools + Memory + Controller。本项目：
- LLM ✅ 仅 2 处调用点（`scorer/src/content/profile.ts` 画像、`content/generator.ts` 内容生成）
- Tools ❌ LLM 不调工具，只被调一次生成文本
- 自主循环 ❌ `collector/src/pipeline.ts` 是固定编排（搜索→抓取→抽取→推断→入库→打分）
准确说法是「**LLM 增强的确定性 ETL 流水线 + RAG-lite 事实注入**」，属 Prompt Chaining / Routing 模式。
**这是加分不是减分**——采集场景本就不该上自主循环。但对外口径需对齐。

### 做得好的（有代码证据）
1. `collector/src/net/http.ts` 是全场最佳：AbortSignal.timeout(20s)、指数退避+抖动(1/2/4s + 0-250ms)、Retry-After 优先、429/5xx 才重试、熔断、按域名限流 2s、UA 轮换、代理池。八项加固全齐。
2. 合规真落地（非文档承诺）：robots.txt 自研 RFC 9309 + Crawlee 双保险；unsubscribe HMAC token 注入；投诉率 >0.1% 自动 suspend 域名（Redis TTL 7d）；硬退信拉黑；GDPR 走 DB 级 FK cascade。
3. 防编造闭环：facts.json 注入 → 强制 [F-xxx] → parseOutput 正则提取 → stripFactMarkers 去正文 → 审核页红字。工程化防幻觉，不靠 prompt 祈祷。
4. 打分 v2 带 evidence/confidence（snippet + sourceUrl），PROVIDER_MARKERS 区分「外包给别人」vs「替别人找供应商」（Fabrinet case）。可审计可复现。
5. 凭据干净：全 env、无硬编码、无 .env 入库、llm.ts 不打印 prompt。
6. 部署工程化：CI 自动部署 + 健康检查 fail-closed、双环境隔离、PM2 env 注入下游地址。

### 缺陷清单（P0 → P2）
- **P0-a LLM 调用裸奔**：`llm.ts` 两个 fetch 无 AbortSignal、无 retry、无降级。与 collector 的加固水平反差极大。LLM 挂起 → scorer 无限挂、gateway 只剩 60s 兜底；LLM 挂 → 直接 500。
- **P0-b 零鉴权**：gateway 全部路由从 `X-Tenant-Id` 取租户，无 JWT。8090 演示环境**公开**，任何人可传任意 tenant_id 读他人数据。（TODO §13.5 记录未修）
- **P1-c 无 trace_id**：全仓库 grep 无 trace_id/requestId。4 个微服务 + LLM 调用无法串联定位。
- **P1-d 无 LLM 评测集**：83 个单测全确定性（打分/zod/配额/SDK 映射），LLM 输出质量零回归覆盖。
- **P1-e 生成侧无幂等键**：mailer 用 BullMQ jobId 去重 ✅；scorer `POST /content/generate` ❌，重复点击重复烧 token + 插重复草稿。
- **P1-f CI 只部署不测试**：`.github/workflows/deploy.yml` 无 test/lint 关卡，push 即上线。
- **P2-g 共享包 3 个占位**：`packages/queue`、`ui`、`config` 各 1 行，实际队列逻辑在 `apps/mailer/src/lib/queue.ts`。违反 AGENTS.md §8。
- **P2-h 测试不可复现**：首次 `pnpm test` 失败（db cascade 测试与 scorer e2e 抢同一库），重跑 2 次 12/12 全绿。turbo 并行多包共享同一 PG → 竞态。（TODO §13.3 记录未修）
- **P2-i 看板无法区分 demo/真实数据**：demo 标记只在 seed + raw_payload，前端零展示；8090 公开全是种子数据。
- **P2-j mailer `tsc --noEmit` 约 20 个历史类型错误**：bun build 不做类型检查，掩盖了。
- **P2-k lint 不干净**：真实诊断 121 条（59 import 排序 + 26 非空断言 + 20 格式 + 16 规则）。文档写的「112 文件扫描通过」已过期。

## 生产 8091 启用 JWT 真隔离（傍晚，闭环上文"部署待办"）

上文"生产 8091 仍未注入 AUTH_MODE=required"现已闭环。用户要求用 AUTH_MODE=required 替代 basic auth 兜底，做真正的租户隔离。

### 方案
调研后选 **JWT 模式**（tenant_id 从 token 解析，请求头无法冒充）；API Key 模式 tenant 仍取请求头、隔离不彻底，弃用。仅 prod 启用，demo 保持 off。

### 改动（本地改 → rsync 到服务器，排除 apps/*/.env 以免覆盖服务器正确的 dashboard tenant）

2. 新增 `apps/gateway/src/routes/auth.ts`：`POST /api/auth/token`，从 nginx 透传的 `Authorization: Basic` 解用户名，用 JWT_SECRET 签 HS256 JWT（sub + tenant_id + exp=12h）。
3. `apps/gateway/src/index.ts`：`app.route('/api/auth', authRoutes)`。
4. `apps/dashboard/src/lib/api.ts`：lazy token——首请求遇 401 自动调 /api/auth/token（浏览器带 basic auth）拿 JWT 缓存、重发带 Bearer；demo off 首请求 200 不触发，一份前端兼容 8090/8091。

- `pcb-prod.conf`：location /api/ 加 `proxy_set_header Authorization $http_authorization;` 透传 basic auth 给 token 端点。

验证后删测试租户（级联删其公司）、杀临时进程，残留 0。证明：即便持合法签发的租户 B 的 JWT，也读不到租户 A 数据；客户端用请求头声明租户无法越权。
